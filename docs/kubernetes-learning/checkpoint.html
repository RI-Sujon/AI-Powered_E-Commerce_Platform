K1 · Pods, Deployments, Services
Why does a Service route to Pods by label selector instead of by Pod name?
Pod names are randomly suffixed and disposable — a Pod that dies and gets replaced gets a new name. If a Service routed by name, it would break on every single Pod restart. Labels are just tags a Pod carries; the Deployment stamps the same labels onto every replacement Pod, so the Service's routing table stays correct with zero reconfiguration.
What breaks if a Deployment's selector.matchLabels doesn't match its own template.metadata.labels?
The Deployment creates Pods it can no longer see or manage — selector is how it finds "its own" Pods afterward. These two blocks aren't structurally linked; they only work because they're kept in sync by convention.
What's the actual difference between a Service's port and targetPort?
port is what a client connects to on the Service's own stable address. targetPort is what the container itself listens on. They're allowed to differ — a Service can expose 80 while forwarding to a container listening on 8080.
K2 · ConfigMaps, Secrets, PVCs
Does writing a Secret with stringData instead of data change what's actually stored?
No. stringData is a write-only convenience — you author plaintext, and Kubernetes base64-encodes it into data on apply. What's actually sitting in etcd is identical either way: base64, not encryption.
What's the difference between a Pod's volumes and a container's volumeMounts?
volumes (Pod-level, alongside containers) declares "this storage exists and is available to this Pod." volumeMounts (inside one specific container) says "mount it at this path, inside me." A Pod with multiple containers could mount the same volume at different paths in each.
Why does Postgres get a PVC in this project, but Redis deliberately doesn't?
Redis is used purely as a cache, and the app already falls back to in-memory caching if it's unreachable — losing cached data on a restart is expected and fine. Postgres holds real data with no fallback, so losing it on a restart would be an actual data loss, not just a cache miss.
K3 · Probes
Why must a liveness probe never check a downstream dependency like Postgres?
Liveness failing causes a restart. If liveness depended on Postgres, a Postgres outage would make Kubernetes repeatedly kill and restart a perfectly healthy API process — which does nothing to fix Postgres, and just throws away warm state for no benefit. Liveness should only ever answer "is my own process stuck."
What's the practical difference in consequence between a failed readiness probe and a failed liveness probe?
Readiness failing: the Pod is pulled from the Service's endpoint list, but the container keeps running — cheap and fully reversible. Liveness failing: the container is actually killed and restarted — expensive and disruptive if it fires wrongly.
Why does Postgres use an exec probe instead of httpGet?
Postgres doesn't speak HTTP. An exec probe runs a command inside the container and checks its exit code — using pg_isready specifically means the probe matches what Postgres's own tooling considers "ready," not a guess from outside.
K4 · Ingress
Why does routing /api through the Ingress need zero path rewriting?
Every API controller in this project is already rooted at api/[controller]. The Ingress path and the app's own route already agree, so the path that hits the Ingress is exactly the path forwarded to the Service — no rewrite rule needed.
Why did setting Web's ApiBaseUrl to an empty string fix the browser's API calls?
It collapsed `${window.API_BASE_URL}/api/product` into a relative URL. A relative URL resolves against whatever origin actually served the page — so once the page came through the Ingress, a relative /api/... call from that same browser tab reaches the Ingress too. The old value, http://ecommerce-api:8080, was cluster-internal DNS a browser could never resolve.
K5 · Kustomize
What does an overlay's namespace: ecommerce-prod field actually do to the base's kind: Namespace resource?
Two things in one line: it sets metadata.namespace on every namespaced resource, and — because the base's namespace.yaml is itself a Namespace object — it renames that object's own metadata.name to match. That special case is why nothing in base/ needed to change to support three separate namespaces.
What's the difference between JSON6902's op: replace and op: add?
replace requires the target path to already exist — it swaps the value. add creates a new field. The prod overlay uses add for the Ingress host specifically because base's ingress.yaml has no host key at all until an overlay adds one.
K6 · Autoscaling
Why couldn't 40 concurrent HTTP requests trigger the HPA, but a shell busy-loop inside the container could?
The product-list endpoint just isn't CPU-heavy — most of its time is I/O wait (DB round-trip), not CPU work, so even real concurrent traffic never pushed usage near the 50% target. A tight while true; do :; done loop is pure CPU burn with no I/O wait at all, so it saturates the container's CPU almost instantly — proving the autoscaler mechanism itself, independent of how expensive any one endpoint happens to be.
Why does an HPA scale up almost instantly but wait roughly 5 minutes before scaling back down?
Scaling up fast is cheap insurance against real load. Scaling down fast risks flapping — dropping a replica the instant load dips, then immediately needing it back. The default stabilizationWindowSeconds: 300 only applies to scale-down decisions; scale-up has no such default delay.

Hands-on challenges

Run these for real against the cluster — it's still up. Each has a hint, not a full answer; open it only if you get stuck. Checked state is remembered on this device only.

1. Prove readiness and liveness really are independent

Scale Postgres to 0 replicas. Watch the API Pod's own status and the Service's endpoint list at the same time. Then bring Postgres back and watch it recover — with no restart at any point.

hint
You need two terminals (or two commands in sequence): one polling kubectl get pods -n ecommerce -l app=ecommerce-api, the other polling kubectl get endpoints ecommerce-api -n ecommerce. Scale with kubectl scale deployment/postgres -n ecommerce --replicas=0.
2. Break the label match on purpose (then fix it)

Temporarily change web-deployment.yaml's template.metadata.labels.app to something else, apply it, and see what happens to the existing Pod and the Service's endpoints. Revert before moving on.

hint
Only template.metadata.labels needs to change for this test — leave selector.matchLabels alone, since that's the mismatch you're trying to create. Watch kubectl get endpoints ecommerce-web -n ecommerce before and after.
3. Trace one request end-to-end

Pick one curl http://localhost/api/product/get-product-list and account for every hop it takes — Ingress, Service, Pod — using only kubectl commands, no guessing.

hint
kubectl get ingress -n ecommerce for the routing rule, kubectl get endpoints ecommerce-api -n ecommerce for which Pod IP it resolves to, then kubectl logs on that specific Pod to see the request actually land.
4. Diff two overlays, field by field

Render dev and prod and account for every single line that differs between them — match each one back to a specific patch in overlays/prod/kustomization.yaml.

hint
diff <(kubectl kustomize k8s/overlays/dev) <(kubectl kustomize k8s/overlays/prod) — count the distinct changed sections before you open the overlay file, then check your count.
5. Find where the 5-minute scale-down wait is configured

The HPA doc mentions a default stabilizationWindowSeconds: 300 for scale-down. It isn't written anywhere in this project's YAML — find out where that default actually lives, and what field you'd add to change it.

hint
Look at kubectl explain hpa.spec.behavior.scaleDown — the field doesn't need to exist in your YAML for the default to apply.
