K1

Pods, Deployments, Services

Get the API running as a Pod instead of a process, and give it a network identity that survives the Pod being replaced.

namespace.yaml api-deployment.yaml api-service.yaml
k8s/base/namespace.yaml
# A Namespace is just a named partition inside the cluster - lets you group this app's
# objects together and keep them separate from anything else running in the same cluster
# (kube-system, other projects, etc). Everything else in k8s/ targets this namespace.
apiVersion: v1
kind: Namespace
metadata:
  name: ecommerce
k8s/base/api-deployment.yaml — the shape this started as (probes and envFrom came in K2/K3, see below)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: ecommerce-api
  namespace: ecommerce
  labels:
    app: ecommerce-api
spec:
  replicas: 1
  selector:
    matchLabels:
      app: ecommerce-api    # must match template.metadata.labels below
  template:
    metadata:
      labels:
        app: ecommerce-api  # the label the selector above is looking for
    spec:
      containers:
        - name: api
          image: ecommerce-api:k3-local
          imagePullPolicy: IfNotPresent
          ports:
            - containerPort: 8080
k8s/base/api-service.yaml
apiVersion: v1
kind: Service
metadata:
  name: ecommerce-api
  namespace: ecommerce
spec:
  type: ClusterIP        # internal-only - not reachable from outside the cluster
  selector:
    app: ecommerce-api    # routes to any Pod carrying this label - not by name
  ports:
    - port: 8080          # what callers inside the cluster connect to
      targetPort: 8080    # what the container itself listens on
FieldWhat it actually does
apiVersionWhich API group defines this resource type. Built-in core types (Namespace, Pod, Service) use bare v1; almost everything else lives in a named group + version, e.g. Deployments are apps/v1. Get this wrong and the API server rejects the whole file — it's not cosmetic.
selector vs template.labelsTwo independent blocks that must agree by convention, not by any structural link. The Deployment only knows which Pods are "its own" by matching selector.matchLabels against whatever labels a Pod happens to carry. Let them drift apart and the Deployment creates Pods it can no longer see or manage.
port vs targetPortTwo different addresses that happen to match here. port is what a client connects to on the Service's own stable IP; targetPort is what the container actually listens on. They're allowed to differ — a Service can expose 80 while forwarding to a container listening on 8080.
ClusterIPThe default, most restrictive Service type — gets a stable virtual IP and DNS name, but only routable from inside the cluster. K4's Ingress is what eventually made the app reachable from outside, without changing this Service at all.
insightA Service doesn't know or care about Pod names — every Pod name is randomly suffixed and disposable. It only ever routes by matching labels. That's the entire mechanism behind "a Service survives a Pod restart": the old Pod dies, a new one comes up with the same labels, and the Service's routing table updates itself with zero configuration.
K2

ConfigMaps, Secrets, PersistentVolumeClaims

Move Postgres and Redis in-cluster (off Azure), split configuration by trust level, and give Postgres storage that survives a Pod being replaced.

app-config.yaml app-secrets.yaml postgres-pvc.yaml postgres-deployment.yaml postgres-service.yaml redis-deployment.yaml redis-service.yaml web-deployment.yaml web-service.yaml
k8s/base/app-config.yaml (ConfigMap) — app-secrets.yaml (Secret), side by side
# app-config.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
  namespace: ecommerce
data:
  ASPNETCORE_ENVIRONMENT: "Development"
  Jwt__Issuer: "ECommerceProject"
  Jwt__Audience: "ECommerceProjectUsers"
  Jwt__ExpiryMinutes: "60"

# app-secrets.yaml
apiVersion: v1
kind: Secret
metadata:
  name: app-secrets
  namespace: ecommerce
type: Opaque
stringData:
  postgres-password: "K8sLearning@123"
  jwt-key: "k8s-learning-local-key-not-a-secret-..."
  db-connection-string: "Host=postgres;Port=5432;..."
  redis-connection-string: "redis:6379"
how api-deployment.yaml actually consumes each one — deliberately different
envFrom:
  - configMapRef:
      name: app-config      # dumps EVERY key as an env var - fine, none of it is sensitive
env:
  - name: ConnectionStrings__DefaultConnection
    valueFrom:
      secretKeyRef:
        name: app-secrets
        key: db-connection-string  # hand-picks ONE key - not the whole Secret
k8s/base/postgres-pvc.yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: postgres-data
  namespace: ecommerce
spec:
  accessModes:
    - ReadWriteOnce      # one node mounts it read/write at a time - fine for 1 Postgres Pod
  resources:
    requests:
      storage: 1Gi
postgres-deployment.yaml — wiring the PVC into the actual Pod
env:
  - name: PGDATA
    value: "/var/lib/postgresql/data/pgdata"  # subdirectory, not the mount root - see below
volumeMounts:
  - name: postgres-storage
    mountPath: /var/lib/postgresql/data     # where it appears INSIDE this container
volumes:                                    # Pod-level: declared once, outside `containers`
  - name: postgres-storage
    persistentVolumeClaim:
      claimName: postgres-data          # links back to the PVC by name
FieldWhat it actually does
envFrom.configMapRefBulk import — every key in the ConfigMap becomes an env var, no picking and choosing. Only safe because nothing in a ConfigMap is meant to be sensitive.
env[].valueFrom.secretKeyRefOne key at a time, named explicitly by both name (the Secret) and key (which field inside it). A Pod that doesn't declare a given key never receives it — that's real access-scoping, not just organization.
stringData vs dataA Secret's real storage format is always base64 (data). stringData is a write-only convenience — you author plaintext, Kubernetes base64-encodes it on apply. kubectl get secret still won't print values back; that's convenience, not encryption (values sit in etcd as base64, trivially reversible).
volumes vs volumeMountsTwo-step indirection that trips people up the first time: volumes (Pod-level, a sibling of containers) says "this storage exists and is available to this Pod, call it X." volumeMounts (inside a specific container) says "mount X at this path, inside me." A Pod with 3 containers could mount the same named volume at 3 different paths.
accessModes: ReadWriteOnceOnly one node can mount the volume read-write at a time. Irrelevant on a 1-node kind cluster, but it's the setting that would matter the moment Postgres ever needed to run on a multi-node cluster.
insightThe PVC isn't theoretical — it was actually tested: a product was added through the real API, the Postgres Pod was deleted outright (kubectl delete pod), a brand-new Pod came up with a different name and IP, and the product was still there. The Deployment replaced the Pod; the PVC is what made the data survive that replacement. This same phase also surfaced a real bug (a pooled DB connection left pointing at the now-dead old Pod, failing exactly once) — that specific failure is what K3's probes exist to prevent.
K3

Probes

Stop Kubernetes from guessing whether a Pod is healthy — three different questions, three different endpoints, three different consequences on failure.

api-deployment.yaml web-deployment.yaml postgres-deployment.yaml redis-deployment.yaml
api-deployment.yaml — all three probes
startupProbe:
  httpGet: { path: /health, port: 8080 }   # DB-dependent - same check as readiness
  periodSeconds: 5
  failureThreshold: 12       # 12 x 5s = 60s grace for boot + first DB check
readinessProbe:
  httpGet: { path: /health, port: 8080 }   # DB-dependent - pulls Pod from Service if this fails
  periodSeconds: 5
  timeoutSeconds: 5
  failureThreshold: 2        # quick to pull out of rotation - cheap, reversible
livenessProbe:
  httpGet: { path: /health/live, port: 8080 } # NOT DB-dependent - deliberately
  periodSeconds: 15
  timeoutSeconds: 5
  failureThreshold: 3        # slower to restart - expensive, disruptive
postgres-deployment.yaml / redis-deployment.yaml — the non-HTTP version
readinessProbe:
  exec:
    command: ["pg_isready", "-U", "postgres"]  # runs INSIDE the container; exit 0 = healthy
  periodSeconds: 5
  failureThreshold: 2
FieldWhat it actually does
startupProbe"Has this container finished booting?" While it's failing, readiness/liveness aren't evaluated at all — protects a slow first boot from being killed before it had a chance.
readinessProbe"Should this Pod get traffic right now?" On failure: pulled from the owning Service's endpoint list. Container keeps running — cheap and fully reversible.
livenessProbe"Should this container be killed and restarted?" On failure: an actual restart. The one probe that's expensive and disruptive if it fires wrongly.
httpGet vs exechttpGet makes a real HTTP request to a path/port. exec runs a command inside the container and checks its exit code — for anything that doesn't speak HTTP (Postgres, Redis), using the tool's own official health command (pg_isready, redis-cli ping) means the probe matches what that tool itself considers healthy.
periodSeconds / failureThresholdHow often to check, and how many consecutive failures before acting. period × threshold is the real reaction time — readiness here reacts in ~10s, liveness in ~45s, on purpose (readiness should be twitchy, liveness should not).
insightThe one rule this whole phase is built around: liveness must never check a downstream dependency. If liveness pointed at /health (DB-dependent) like readiness does, a Postgres outage would make Kubernetes repeatedly kill and restart a perfectly healthy API process — which does nothing to fix Postgres, and just discards warm state for no benefit. Verified for real: Postgres was scaled to 0 for 30+ seconds. The API Pod's RESTARTS stayed at 0 the entire time (liveness on /health/live never noticed), while it correctly vanished from the Service's endpoint list (readiness on /health caught it immediately) — then reappeared automatically, same Pod, the moment Postgres came back.
K4

Ingress

Give Web and the API one externally-reachable address, so the browser's own client-side JavaScript can actually call the API — it never could before this.

ingress.yaml web-deployment.yaml (ApiBaseUrl)
k8s/base/ingress.yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: ecommerce-ingress
  namespace: ecommerce
spec:
  ingressClassName: nginx      # which installed controller should read these rules
  rules:
    - http:
        paths:
          - path: /api
            pathType: Prefix
            backend:
              service:
                name: ecommerce-api
                port: { number: 8080 }
          - path: /
            pathType: Prefix
            backend:
              service:
                name: ecommerce-web
                port: { number: 8080 }
web-deployment.yaml — one env var, before → after
# K2:  value: "http://ecommerce-api:8080"   -> cluster-internal DNS, browser can never resolve it
# K4:  value: ""                         -> browser calls a RELATIVE path instead
FieldWhat it actually does
ingressClassNameMatches the class name the ingress-nginx Helm chart registers by default. Needed the moment more than one Ingress controller could exist in a cluster — otherwise nothing says which controller owns these rules.
path + pathType: Prefix"Anything starting with this string." /api matches /api/product/get-product-list and everything else under it. No rewriting happens — the path that hits the Ingress is the exact path forwarded to the Service, which is why this works with zero code changes: every API controller is already rooted at api/[controller].
backend.service.port.numberWhich Service, and which of its ports, receives the traffic for that path rule.
ApiBaseUrl = ""Collapses `${window.API_BASE_URL}/api/product` (in every client-side service file) into a relative URL. The browser resolves a relative URL against whatever origin actually served the page — so once the page came from the Ingress, /api/... from that same browser tab reaches the Ingress too.
insightThe Ingress controller (the real nginx process) isn't in this repo at all — it's installed once via helm install ingress-nginx ..., the same category of "someone else's software" as the Postgres/Redis images. Only the Ingress resource above (the routing rules) is ours to own and commit. Verified live: curl http://localhost/api/product/get-product-list — the exact relative call the browser's own JS makes — returned real data through the same origin that would have thrown a network error before this phase.
K5

Kustomize

One base manifest set, patched — never copied — into dev/staging/prod, mirroring the real Terraform environment split.

base/kustomization.yaml overlays/prod/kustomization.yaml overlays/dev/kustomization.yaml overlays/staging/kustomization.yaml
k8s/base/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization

resources:
  - namespace.yaml
  - app-config.yaml
  - app-secrets.yaml
  - postgres-pvc.yaml
  - postgres-deployment.yaml
  # ...every other file from K1-K4, listed once
  - ingress.yaml
k8s/overlays/prod/kustomization.yaml — every patch type this project uses
resources:
  - ../../base                      # pulls in the entire base list above, unmodified

namespace: ecommerce-prod         # see glossary - does two things at once

patches:
  - target: { kind: ConfigMap, name: app-config }
    patch: |-
      - op: replace
        path: /data/ASPNETCORE_ENVIRONMENT
        value: Production

  - target: { kind: Ingress, name: ecommerce-ingress }
    patch: |-
      - op: add
        path: /spec/rules/0/host
        value: prod.ecommerce.local

  - target: { kind: Deployment, name: ecommerce-api }
    patch: |-
      - op: replace
        path: /spec/replicas
        value: 2
      - op: replace
        path: /spec/template/spec/containers/0/resources
        value:
          requests: { cpu: "200m", memory: "384Mi" }
          limits:   { cpu: "1000m", memory: "768Mi" }
FieldWhat it actually does
resources: [../../base]"Start from everything the base kustomization.yaml lists." Nothing is copied — this is a live reference, so a future change to any base file automatically flows into all three overlays.
namespace: ecommerce-prodDoes two things in one line: sets metadata.namespace on every namespaced resource, and — because the base's own namespace.yaml is itself a kind: Namespace object — renames that object's metadata.name to match. That special case is why nothing in base/ needed to change to support three separate namespaces.
patches[].targetWhich existing resource this patch applies to, matched by kind + name — the resource has to already exist somewhere in resources: (here, pulled in from base).
op: replace / addJSON6902 patch operations. replace requires the path to already exist (swaps its value). add creates a new field — used for the Ingress host because base's ingress.yaml has no host key at all until an overlay adds one.
path: /spec/rules/0/hostA JSON pointer into the resource's own YAML structure. /0/ means "the first item in that array" — here, the Ingress's first (only) rule.
insightdev's and staging's overlays patch only the namespace, the environment name, and the Ingress host — nothing about sizing, because the real dev.tfvars and staging.tfvars are identical to each other except for environment name too. prod is the only one that's genuinely different. Verified live: applying overlays/prod created 2 API + 2 Web Pods with exactly the patched CPU/memory, running with ASPNETCORE_ENVIRONMENT=Production — which then correctly refused to auto-migrate its brand-new empty database (that auto-migrate step is itself gated to Development only, in the app's own Program.cs). Fixed the real way a prod migration should happen: kubectl port-forward to Postgres, then an explicit dotnet ef database update from outside the Pods.
